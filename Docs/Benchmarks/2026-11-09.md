## 1. Where the context goes

- `get_file` returned 51% of all tool output.
- Whole reads of files longer than 300 lines were 33 calls, but 19% of the output, and 21% of the

looked for imports, and the `Imports:` line already covers them), and declaration links (#461), a

## 4. Why P2 and R1 got worse, and #518

**P2, `rich/progress.py` (1,717 lines).** No build ever read it whole: the agent went straight to the
line numbers from search, for example 772 to 817 for `TimeRemainingColumn`. The map arrived on the
first ranged read, about 80 declarations and 4 to 5 thousand characters, and the number of reads
did not fall. The agent already knew where to look.

**R1, `json_deserializer.rs` (429 lines, 14.3 thousand characters).** Without the map: one whole
read. With it: the map and two to four pieces, 10.7 to 12.5 thousand characters in more calls. Just
over the threshold, the map saves almost nothing.

**#518 tuned the map:** threshold raised from 12,000 to 20,000 characters, a compact map of top-level
entries with member counts when there are more than 40, and on ranged reads the map only from the
third read of the same file, so an agent that arrives from search line numbers does not get it,
and one that pages through a file does.

## 6. Notices and other waste

Lines outside the data block, repeated in every response and carried to the end of the session,
are 6.7% of all context. The largest: the untrusted-content header (848 times, 1.5%), the
`[Next read]` batching hint (139 times, 0.4%, a call form agents do not take), `[Symbols]
annotated=…` (241 times, 0.3%). The header is part of the prompt-injection boundary, so it may only
be shortened, never removed.

Checked and not worth doing: an "empty here, matches elsewhere" hint (13% of searches were empty,
and every one checked was a true "nowhere"; 10 of them were patterns rg could not parse), and
wider context in search results (28% of reads repeat lines search had shown, but the agent wanted a
wider piece, so no call is saved).

## 7. Faster dependency indexing (#517, #520)

Performance work with one fixed rule: results byte-identical, measured as medians of alternating
separate processes over 16 views (DevProjex, Repomix, Flask and click × full, `src/`, extension
filter, `git_scope`).

**Rejected candidates of #489:**

| Candidate | Why |
|---|---|
| Reuse the scan inventory instead of listing folders again | Even an optimistic prototype was not faster beyond the spread in any of 8 cases |
| Fixed config names checked once | On Windows `TSCONFIG.JSON` was read and a relation became Resolved instead of Unresolved, a change of result |
| Skip discovery for a full manifest | Same results, no speed-up beyond the spread |
| Merge directory marks | Broke invalidation: after `pyproject.toml` was created, a stale Unresolved stayed instead of External; an existing test caught it |

The tests that pin those behaviours were kept.

**#517, parallel content hashing before ranking.** DevProjex ranking cold 4,737 → 4,427 ms, warm
554 → 311 ms; Repomix cold 807 → 722 ms, warm 295 → 227 ms. 448 processes confirmed equal results.

**#520, bounded pipeline for cold extraction.** It was first rejected by a gate that allowed no warm
slowdown at all, for a warm cost of 3 to 7 ms against a cold saving of about a second. With the
gate restated (cold faster beyond the spread, warm at most +10% and at most +10 ms, results
byte-identical) and the pipeline never built on the warm path:

| First `related_files` on DevProjex | Cold | Warm |
|---|---|---|
| Whole project | 3,846 → 2,801 ms | 66 → 70 ms |
| `Application/` | 3,903 → 3,016 ms | 76 → 81 ms |
| Extension filter | 4,280 → 3,384 ms | 99 → 106 ms |
| `git_scope` | 3,875 → 2,815 ms | 75 → 76 ms |

Repomix, Flask and click stayed within ±4%. All 16 results byte-identical. **Kept.**

## Lessons

- **Calls drive the cost.** Each call resends the accumulated context, 28 to 34 thousand tokens per
  turn on average here; an extra call costs more than reading a large file whole (about 4 thousand
  tokens).
- **Replace content, do not add to it.** The large-file map pays when it stands in for a whole read
  and costs when it is added to a ranged read the agent had already aimed.
- **A new listing is a new to-do list.** #519 is the third case after the affected-files section and
  the rename.
- **Unseen repositories are the honest check.** The hono precision gap did not exist on rich and
  FluentValidation.
