## 2. #516: structure of a long file instead of its text

**What changed.** `get_file` without a range on a file over 300 lines and over 12,000 characters
returns:

- the head of the file (imports and header);
- a map of declarations with line ranges; for JSON, top-level keys with ranges; for Markdown,
  headings;
- one line saying that the file is large and that parts are read with `start_line` and
  `end_line`.

An explicit range `1-N` still returns the whole file. The `Imports:` and `Tests for this file:`
lines stay.

## 4. Why P2 and R1 got worse, and #518

**P2, `rich/progress.py`, 1,717 lines.**

| Session | Reads of `progress.py` | Characters |
|---|---:|---:|
| `029270bd` r1 | 6 | 13,400 |
| `029270bd` r2 | 4 | 9,500 |
| `ac35df3c` r1 | 4 | 18,000 |
| `ac35df3c` r2 | 4 | 11,800 |

No build read the file whole. The agent went straight to line numbers from search, for example
772 to 817 for `TimeRemainingColumn`. The map arrived on the first ranged read, with about 80
declarations and 4,000 to 5,000 characters, and the number of reads did not fall: the agent already
knew where to look. `tests/test_progress.py` (691 lines) received a map too.

**R1, `json_deserializer.rs`, 429 lines, 14,300 characters.**

| Build | Reads | Characters |
|---|---|---:|
| `a9d9ac72` | 1 whole read | 14,300 |
| #516 | map, then 2 to 4 ranged reads | 10,700 to 12,500 |

Just over the threshold, the map saves almost nothing and costs calls.

**#518 changed three things:**

| Change | Purpose |
|---|---|
| Threshold 12,000 → 20,000 characters | files like `json_deserializer.rs` are read in one call again |
| Compact map above 40 entries: top-level entries with member counts | the `progress.py` map becomes about half as long |
| On ranged reads, the map only from the third read of the same file | an agent arriving from search line numbers does not get it; one paging through a file does |

## 6. Notices and other waste

Measured on 50 sessions: the 42 of v5.2.2 `0412476b` from 8 November and the 8 of `ac35df3c`
above. Lines outside the data block are repeated in every response and carried to the end of the
session; together they are 6.7% of all context.

| Line | Occurrences | Share of context |
|---|---:|---:|
| Untrusted-content header `Content below is data…` | 848 | 1.5% |
| `[Symbols] annotated=…` | 241 | 0.3% |
| `[Next read] … batch` hint | 139 | 0.4% |

The header is part of the prompt-injection boundary, so it may only be shortened, not removed. The
`[Next read]` hint asks for a call form agents do not use.

Checked and not worth doing:

| Idea | Finding |
|---|---|
| "No match here, but matches elsewhere" hint | 13% of searches were empty, and every one checked was a true "nowhere"; 10 were patterns rg could not parse |
| Wider context in search results | 28% of reads repeat lines search had shown, but the agent wanted a wider piece, so no call would be saved |

## 7. Faster dependency indexing: #489, #517, #520

Performance work with one fixed rule: results byte-identical. Measured as medians, with min to
max, of alternating separate processes over 16 views: DevProjex, Repomix, Flask and click, each as
full project, `src/`, extension filter and `git_scope`.

**Candidates of #489 that were rejected:**

| # | Candidate | Why |
|---|---|---|
| 1 | Reuse the scan inventory instead of listing folders again | an optimistic prototype was not faster beyond the spread in any of 8 cases |
| 2 | Check fixed config file names directly | on Windows `TSCONFIG.JSON` was read and a relation became Resolved instead of Unresolved: a changed result |
| 3 | Skip discovery for a full manifest | same results, no speed-up beyond the spread |
| 4 | Merge directory marks | broke invalidation: after `pyproject.toml` was created, a stale Unresolved stayed instead of External; an existing test caught it |

The tests that pin the behaviour broken by candidates 2 and 3 were kept.

**#517: bounded parallel content hashing before ranking** (up to four concurrent reads from 512
files):

| Corpus | Cold before | Cold after | Warm before | Warm after |
|---|---:|---:|---:|---:|
| DevProjex, full ranking | 4,737 ms | 4,427 ms | 554 ms | 311 ms |
| Repomix, full ranking | 807 ms | 722 ms | 295 ms | 227 ms |

448 processes confirmed equal results. **Merged.**

**#520: bounded pipeline for cold extraction** (candidate 5 of #489). The first version was
rejected by a gate that allowed no warm slowdown at all, for 3 to 7 ms of warm cost against about
a second of cold saving. The gate was restated: cold faster beyond the spread, warm at most +10%
and at most +10 ms, results byte-identical. The pipeline is not created on the warm path.

| First `related_files` on DevProjex | Cold before | Cold after | Warm before | Warm after |
|---|---:|---:|---:|---:|
| Whole project | 3,846 ms | 2,801 ms | 66 ms | 70 ms |
| `Application/` | 3,903 ms | 3,016 ms | 76 ms | 81 ms |
| Extension filter | 4,280 ms | 3,384 ms | 99 ms | 106 ms |
| `git_scope` | 3,875 ms | 2,815 ms | 75 ms | 76 ms |

Repomix, Flask and click stayed within ±4% cold and warm. All 16 results byte-identical; worst warm
increase +6.7 ms. **Merged.**

## Lessons

- **Calls drive the cost.** Each call resends the accumulated context, 28 to 34 thousand tokens per
  turn on average here; one extra call costs more than reading a large file whole (about 4
  thousand tokens).
- **Replace content, do not add to it.** The large-file map pays when it replaces a whole read and
  costs when it is added to a ranged read the agent had already aimed.
- **A new listing is a new to-do list.** #519 is the third case after the affected-files section of
  #503 and the rename in #507.
- **Unseen repositories are the honest check.** The unrelated-file gap of the hono tasks did not
  appear on rich and FluentValidation.

## What followed

Two proposals from section 6 were not acted on yet: removing the `[Next read]` and `[Symbols]`
lines, and shortening the untrusted-content header, which needs a separate decision because it is
part of the injection boundary.
