# 2026-08-29: calibrating the token estimate

## Why this was measured

DevProjex reports an estimated token count for every file and every pack, and `max_tokens`
budgets are admitted against that estimate. The estimate is characters divided by four. The
question was whether a smaller divisor, such as 3.8, would be closer to real tokenizers.

## Setup

- Real tokenizers through `tiktoken`: `cl100k_base` and `o200k_base`.
- Two corpora: the DevProjex repository (about 17 million characters, mostly C#) and the Python
  standard library (about 11.9 million characters).
- Measured value: characters per token, over the whole corpus and per file type.

## Results

| Corpus | cl100k chars per token | o200k chars per token |
|---|---:|---:|
| DevProjex repository, all files | 4.20 | 4.23 |
| DevProjex repository, `.cs` only | 4.52 | 4.43 |
| DevProjex repository, JSON only | 2.93 | 3.32 |
| Python standard library | 4.02 | 3.98 |

## Decision

**Kept the divisor of 4.**

| Option | Effect | Decision |
|---|---|---|
| Divisor 4 | within about ±5% of both encodings across languages, slightly conservative on code | kept |
| Divisor 3.75 or 3.8 | estimates about 10% higher for GPT models across the board | rejected |

Claude's tokenizer is not published and differs between model versions, so no constant can be
calibrated against it. That case is covered by documentation: the `max_tokens` description asks to
leave headroom when the model's tokenizer is denser.

## What this means for the benchmark log

The divisor is an estimate for budgets, not a measurement of what a model is billed. On
[2026-09-12](2026-09-12.md) it turned out that the benchmark scripts had been reporting
characters divided by four as "tokens"; from 13 September every session total in this log comes
from the token counts that the Claude Code client reports.
