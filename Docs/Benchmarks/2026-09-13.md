# 2026-09-13: separate arms, and the first search body

**Builds:** v5.2 `0cdf95b7`, `1f4796ec`, `581e52f7` · **Other side:** Repomix 1.18.0 · **Agent:**
Claude Haiku 4.5 · **Format:** separate anonymous arms, one server per session

From this day on each session has one server only, named neutrally (`server_v`, `server_w`), and
tokens are what the client reports, not characters divided by four.

## 1. v5.2 against Repomix

**Setup.** Tasks T1, T3, T5, T6, N1 and N2 on httpx 0.28.1, hono v4.13.7 and serilog v4.3.0, two
arms, two repeats: 24 sessions, $3.43.

| Metric | DevProjex / Repomix |
|---|---|
| New context tokens | 419,684 / 439,185 |
| Tool calls | 234 / 214 |
| Turns | 246 / 226 |
| Cost | $1.73 / $1.70 |
| Required paths missed | 13/52 / 22/52 |

**Judge, both orders, a verdict only when they agree.** Correctness: 12 of 12 pairs agreed, 11 to
DevProjex and 1 to Repomix. Preference disagreed between orders on half the pairs; the six that
agreed all went to DevProjex. Correctness is stable; preference is not, so its disagreement rate
has to be quoted with it.

Two claims from two days earlier did not reproduce: the token deficit turned into a small lead,
and "Repomix is cheaper on broad exploration" split (broad T3 cheaper for us, broad T6 for them).
Our own T1 cost 45,824 and 23,299 tokens on two runs of the same task and server, so per-task gaps
under 2x are noise.

**Harness trap.** `run.mjs` skips a job when its `summary.json` already exists, and the arm name
`server_k` had been used on 10 September for the filesystem server on a different model. Four of
our twelve points would have been silently taken from another tool. **Rule:** fresh arm names, or
a clean `runs/` folder, for every series.

Server instructions per number of roots, a glob example for `get_tree`, and a smaller tool catalog.

The predicted cache saving from the lighter prefix was 124,260 tokens; the observed one was
129,577, so the lighter catalog explains the whole drop. Every new session started with a useful
call. The glob example in the instructions was used **0 times** in either arm.

**Kept:** the per-root instructions and the slimmer catalog. **Learned:** instruction text removed a
start step but did not change a working habit. It was the second such failure after the batching
sentence (6 of 103), so routing changes are no longer expected from instruction prose.

## 3. Declaration body in search results (`1f4796ec` → `581e52f7`)

Search returned declaration ranges and the body of the first declaration, up to 1,800 characters.
Tasks T1, T5, T7 and N2, one repeat.

| Metric | Without body / with body |
|---|---|
| Turns | 75 / 61 |
| Calls | 71 / 57 |
| Searches | 31 / 23 |
| Wall time, s | 277 / 228 |
| Response characters | 208,055 / 259,024 |
| Cost | $0.521 / $0.510 |
| Required paths missed | 2/18 / 5/18 |

The first real fall in calls, and a worse coverage. The transcripts showed why: the body went to
the **first declaration in path order**, not the best match. Five of fifteen bodies came from test
or benchmark files; in T7 the query `GetEffectiveLevel` got the body of
`LoggerAuditSinkConfiguration`, the first of 26 candidates, whose name does not contain the term.
The agent stopped earlier, on the wrong material.

**Not rolled back; fixed.** The body now goes to a declaration whose printed name contains the
searched term first, with the old order as the tie-break. A rule of "tests rank lower" was
rejected: it is a category guess, while a name match is a fact. The clean measurement of the
corrected body is on [2026-09-15](2026-09-15.md).
