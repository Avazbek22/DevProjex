## 5. The keys and the judge were wrong

The first judge had produced 1,081 complaints on answers. Three groups made up most of them:

| Complaint | Count | What it really was |
|---|---:|---|
| A required file is missing | 230 | often seen by the agent and dropped; in T5 `bearer-auth` and `cors` appeared in every search but not in the answer |
| A line number or detail cannot be verified | 226 | the judge does not see the code and penalised precision |
| An extra file not in the key | 217 | partly correct files missing from the key |

**Key audit.** Every key was checked against the repository.

| Task | Error in the key |
|---|---|
| T5 | listed `bearer-auth` and `cors` as `c.json` callers; they mention it only in doc comments |
| N1 | listed `test_config.py` and `test_api.py`; they do not read the changed defaults |
| T8 | missed three test implementations of the interface and `LogContext.cs` |
| D1 | missed `cloudflare-pages/handler.ts` and five tests |

**New measuring rules:**

- keys gained `acceptable` and `unrelated` lists;
- judge v3 counts as an error only a contradiction with the key, never an unverifiable detail, and
  applies the same rule to both sides;
- the score against the key (required files, required tests, known-wrong files, calls, tokens)
  is the main metric, the judge a second opinion;
- a change counts as a gain only when an objective metric moves by more than the spread of
  identical code. In one round D1, N2 and T5 behaved the same in both builds and the judge still
  split 6 to 1.

## Lessons

- **Every list becomes a to-do list.** Affected-file sections and dependent lists raise recall and
  wrong files together.
- **An offered call form is not taken.** 0 of 54.
- **A name changes the probe, not the answer.** Count use in full sessions, not in the first ten
  calls.
- **A gate that forbids any slowdown rejects real gains.** State the threshold against what the
  user pays and measure it as a median of alternating runs.
- **Audit the keys before believing a judge.**
