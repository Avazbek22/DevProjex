# 2026-11-12: batch reads that return structure, measured twice

The first series in this log run with Codex CLI, and the first difference in named files that was
repeated on new sessions before it was believed.

## Why

Codex sessions recorded on v5.2.2 showed where batched `get_file` calls lost work. 220 whole-file
batches asked for 1,064 files: 654 arrived whole, 131 were cut and 271 were not returned. In 117
of the 133 batches that overflowed, the limit reached was 1,000 lines. Across all batch reads of
those sessions, a file that was not returned was requested whole again in 138 of 298 cases. The
ready continuation call printed under a cut batch was shown 142 times and used 0 times. Four call
forms ended in an error: a ninth file against the limit of eight, a line range sent with several
paths, a regular expression sent with `symbols`, and a folder sent to `related_files`.

#545 changed what a batch returns and made those forms work:

- A batch takes up to sixteen files and has one limit, 50,000 characters.
- A large file (more than 300 lines and 20,000 characters) returns its start and its structure
  with line ranges; a file that no longer fits returns its structure instead of nothing.
- A line range sent with several paths is read from each of them, and `path` or `paths` can
  accompany `requests`.
- A regular expression sent with `symbols` runs as a text search and says so.
- A folder given to `related_files` stands for the files directly inside it.
- A search that cannot print every match always keeps room for the per-file counts of the rest.
- The structure of JavaScript and TypeScript test files lists `describe` and `it` blocks.
- The `Exported by:` line follows `tsconfig` `rootDir` and `outDir`, so a built entry point is
  traced back to its source file.
- Seven descriptions were reworded; `list_projects` now says it is not needed with one
  configured root.

## Decisions

- **Kept:** #545, merged as `cee97db7`.
- **Not done:** rolling back structure or the new descriptions because of the first series; the
  difference did not repeat. A sentence about batching in the `get_file` description is not
  restored either: three sessions of one task are not a measured cause.
- **Still unmeasured:** Claude Code sessions on the new batch, and answer quality as a judge
  would rate it; both series used key metrics only.

## Lessons

- **A difference seen once in five sessions per task is a hypothesis.** Eight fewer required
  files of 150 disappeared on ten new sessions per task. One path named in every earlier session
  and in 3 of 5 once was noise as well.
- **Set the thresholds before the run and decide on the new sessions only.** Pooled with the
  first series, T3 still reads 58/60 against 56/60; the pooled number repeats the difference that
  prompted the second run and decides nothing.
- **A sentence in a tool description did what the same advice in the server instructions had
  not.** The instructions already said to skip `list_projects` with one root, and the call was
  made 27 times in 80 sessions; with the sentence in the tool's own description it was made 0
  times in 80.
